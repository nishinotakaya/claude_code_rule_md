# 分割と重複の判断（オブジェクト指向）

> 関係するものを役割ごとにひとかたまりにし、何がどこにあり誰が担当かを見た瞬間に分かるようにする。

## 判断ルール

| ルール | 中身 |
|---|---|
| 1 ファイル = 1 つの役割 | `app.js` / `utils.rb` のような中身が予測できない名前、5 クラス同居、指揮者と部品の同居は NG |
| 機能を外側に（feature folder） | `pages/users/article/`、`components/admin/` のように機能で閉じる。横断は `shared/` `lib/` |
| ファイル名 = クラス名 = 役割名 | ディレクトリが namespace なら prefix を重ねない（`admins/articles_controller.rb`）。エンティティ名は例外 |
| データと振る舞いを同居させる | 保存・取得はデータを持つクラス（Store / Repository / モデル）の責任。画面から直接 localStorage / API を叩かない |
| コピペは 2 回まで | 3 回目が見えたら抽出。1〜2 回で慌てて抽象化しない（過剰抽象化は認知負荷） |
| 「追加用」「編集用」を別々に作らない | 違いが文言だけなら 1 つのフォーム / モーダルを mode で切り替える |
| 共通部品（`shared/` `components/*Layout`）は極力触らない | 構造的な入力タイプの追加は OK。文言などの cosmetic な上書き口（`local_assigns[:x] \|\| 既定`）は足さない |
| パーシャル化したつもりを作らない | 実際に render / import されていなければ直書きとの重複 |

## 抽出の基準

- ✅ 3 か所以上で同一の制御フローが繰り返されている
- ✅ `if/else` の引数差 < 共通部分
- ❌ 名前は似ているが処理が違うものを無理に抽出しない（Wrong Abstraction より重複の方がまし）

## リファクタの鉄則

- **動作を変えない。** エラーメッセージ・ステータスコード・レスポンス形式・DB トランザクションは不変
- ついでのバグ修正・仕様変更は別コミット
- 抽出後は呼び出し全パスを実行して確認してから終える
- 「あとでリファクタ」は「やらない」と同義。今やる。ただし OO 的な正しさのために動くコードを壊さない

## 進め方

観察（ファイル・行・責任の棚卸し）→ 分割案の提示と合意 → 1 ステップずつ実行し動作確認 → 中途半端なフォルダ・未使用ファイルを残さない
