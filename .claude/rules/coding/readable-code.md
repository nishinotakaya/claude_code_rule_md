# 読みやすさの原則（『リーダブルコード』より）

コードは「他の人が最短時間で理解できるように」書く。他の人には 6 か月後の自分も含む。命名・コメントの具体規約は `naming.md` / `comments.md` が優先。

## 制御フロー

- 条件式は左に変化する値、右に安定した値（`length >= 10`）
- ガード節（早期 `return` / `next`）でネストを浅くする。ネストが増える変更は見直しの合図
- 三項演算子は 1 行で読み切れるときだけ。巧妙な書き方より素直な書き方
- 否定形のブール（`not_active`）を避ける。`!user.not_active?` を書いた時点で負け

## 式と変数

- 巨大な式は説明変数・要約変数に分ける（`user_owns_document = ...`）
- `!(a && !b)` はド・モルガンで `!a || b` に
- 役に立たない一時変数・制御フロー変数（`done`）を消す。使う直前で定義し、再代入を減らす（JS は `const` 既定）

## 関数

- 無関係の下位問題（整形・変換・日付計算）は別関数へ。共通 util への昇格は **3 か所見えてから**
- 一度に 1 つのこと。列挙 → 分割 → 残りは空行で段落化（取得 → 変換 → 保存）
- 書く前に簡単な言葉で説明し、その語を名前と構造にする。説明できない = 理解不足
- 最も読みやすいのは書かれていないコード。標準ライブラリ・既存コードを再利用し、未使用コードは消す

## テスト

- 入力 → 期待値が 1 画面で読める。詳細はヘルパー / factory へ
- 1 テスト 1 観点。テスト名は「対象 × 状況 × 期待結果」
- テストしにくさは設計の警報。ただしテストのために実装を歪めない

## チェック（書いたら自問）

- [ ] 名前は他の意味に誤解されないか（`filter` / `limit` / `get`）
- [ ] ネストは早期リターンで浅くしたか
- [ ] 巨大な式に名前を付けたか
- [ ] 一度に 1 つのことをしているか
- [ ] そもそも書かずに済むコードではないか
