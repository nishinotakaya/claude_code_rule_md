# STEP 1〜2: 要件理解・影響範囲分析

## STEP 1. 要件理解（重要な判断はデュアル AI）

1. 要件を理解し、方針・技術設計案を策定する。**「何を・なぜ・どこまで」を文章にする**。曖昧な点は実装前に確認する
2. **インターフェース定義**: tester が先にテストを書けるよう明確にする
   - ファイルパス（新規・変更対象）
   - クラス名・関数名・メソッドシグネチャ
   - 入出力の型・期待する振る舞い
   - API の場合: エンドポイント・リクエスト / レスポンス形式（`.claude/rules/project/techput-overview.md` の API 契約に合わせる）
3. `.claude/rules/coding/` と `.claude/rules/security/` から、今回の変更に関連する規約・禁止パターンを抜粋する（全体ではなく該当部分だけ）。認証・認可・外部入力・秘密情報に触れる変更は `/security-baseline` の該当項目も抜粋する
4. **重要な判断は `/dual-ai` で Codex の第二意見を取る**（設計・複数案・DB 変更・API 変更・方針変更）。同じ計画版で重要変更が無く、実装インターフェースまでレビュー済みなら再実施しない
5. 最終方針を確定し、Codex の反論・盲点の採否と理由を記録する。`tasks/todo.md` にチェック項目付きで書く
6. 3 ステップ以上のタスクは、計画を社長（ユーザー）に見せて承認を取ってから着手する。方向違いのやり直しが一番高くつく
7. **検証手段を先に決める**: テストケース・期待出力・スクショなど「できた」の根拠を計画段階で書く。自己検証できると修正往復が減る

## STEP 2. 影響範囲分析

コードを書く前に実施する。調査は researcher に出してよい。

1. **変更対象の特定**: どのファイル・クラス・関数を変更するか列挙する
2. **依存関係の調査**: 変更対象の呼び出し元、変更対象が呼び出す先、**後続でチェーンしている処理**（API を呼んだ直後に別の API を呼ぶフロントのハンドラなど）を grep で洗う
3. **影響範囲の判定**: 波及するモジュール・テスト・画面を特定する。rename / 削除するシンボルは旧名で全体 grep する
4. **リスク評価**:
   - 既存の API レスポンス形式が変わらないか（フロントの型と `*_json` の一致。フィールドは足すだけ。改名・削除は非互換）
   - 既存テストが壊れないか
   - DB スキーマ変更が要るか（マイグレーション・ロールバック・既存データの扱い・バックフィルの順序）
   - 多テナント: `Current.tenant` が nil の経路（マイグレーション・seed・コンソール・rake）を通るか
   - 認可境界: コントローラ / routes を触るなら、アクション × 認証 × ロール × 所有スコープ × 副作用の表を実装前に書く（`/security-baseline` の `references/role-boundary.md`）
   - 旧 ERB 画面（`/users/*` `/admins/*`）に影響しないか
5. **判断**: 他機能に悪影響がある場合は、方針変更か実装中止を選び、理由を社長に報告する

結果は `tasks/todo.md` に記録する。
