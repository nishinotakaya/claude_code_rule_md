# STEP 4.5: テスト先行（TDD）

**実装より先に** tester を起動し、仕様ベースでテストを書かせる。実装コードの diff ではなく STEP 1 のインターフェース定義と変更仕様から書くため、実装バイアスがゼロになる。

## プロンプトに含める情報

```
- 変更仕様（何を実現するか）
- インターフェース定義（ファイルパス・クラス名・メソッドシグネチャ・入出力）
- 既存テストの構成（バックエンド: spec/requests/api/v1/{admin,auth,manager,users}、factory、JwtHelper.encode で Bearer を作る）
- テスト要件（下記）
- worktree のパスとブランチ
- worktree 上でテストコードをコミットすること
```

## テックプットでの現実

| リポジトリ | 機械テスト | 代替 |
|---|---|---|
| バックエンド | RSpec（request spec 中心）。`bundle exec rspec` | — |
| フロント | **テストランナー無し**。`npm run build`（tsc）だけ | 受け入れ基準を Playwright の操作手順に落とし、STEP 10 で qa が実行する |

## 3 フェーズ

### Phase 1: 単体テスト

| 変更内容 | 必須テスト |
|---|---|
| モデル変更 | バリデーション・スコープ・関連・コールバック。テナント境界（他テナントのレコードが default_scope で見えない） |
| ユーティリティ関数 | 入出力の全パターン（nil / 空 / 最大値） |
| バグ修正 | バグを再現するテスト（修正前に失敗、修正後に成功） |

### Phase 2: 結合テスト（request spec）

| 変更内容 | 必須テスト |
|---|---|
| API 追加・変更 | 正常系 + 異常系 + **認証（401）・ロール（403）・他テナント（404 かつ DB 不変）** |
| レスポンス形式 | camelCase・`id` が文字列・`iso8601`・`{ articles: [] }` の包み |
| 一覧 | 並び順が固定されている |

### Phase 3: システムテスト（E2E）

| 変更内容 | 必須テスト |
|---|---|
| ユーザーフロー変更 | Playwright で PC 幅とスマホ幅の操作シナリオ |
| 認証・認可フロー変更 | ログイン〜操作〜ログアウト。ロール違いで入れないこと |

### 適用判断

| 変更規模 | Phase 1 | Phase 2 | Phase 3 |
|---|:---:|:---:|:---:|
| 関数・メソッド単位 | 必須 | 推奨 | — |
| 複数モジュールに跨る | 必須 | 必須 | 推奨 |
| 画面・ユーザーフローに影響 | 必須 | 必須 | 必須 |
| バグ修正 | 必須（再現テスト） | 関連部分 | 関連フローがあれば |

テスト不要: 設定ファイルのみ・ドキュメントのみ・CSS のみ（デザインレビューで担保）。

## tester の出力

1. テスト戦略（どのフェーズをどの観点で。PM が承認する）
2. テスト項目一覧（フェーズ別）
3. テストコード（実装前なので全件 FAIL が正常）
4. カバレッジ見積（何をカバーし、何をしないか）

## 禁止

- 通すためにアサーションを弱める・`skip` / `xit` を足す・期待値を実装に合わせる
- プロダクトコードを変更する（バグを見つけたら「どのテストがなぜ落ちるか」を報告する）
