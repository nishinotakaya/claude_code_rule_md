# コードレビューの観点と伝え方

> 「レビューして」と言われたら `/code-review` を読んでから差分を見る。ここはその要約。

## 始める前

1. 対象ブランチを最新化し、`git log --oneline base..HEAD` で流れを掴む
2. 型・ビルド・テストを自分で回す（`npm run build` / `bundle exec rspec` / `rubocop`）。緑かどうかを最初に押さえる
3. 未コミットの diff が混ざっていないか確認する
4. このプロジェクトには lint も CI も無い（バックエンドは rubocop のみ）。機械が潰す前提の観点（`any`・空 catch・1 文字変数・N+1）も人が見る

## 指摘のラベル（md 報告と総評で使う。行コメントには貼らない）

| ラベル | 意味 | 上限 |
|---|---|---|
| 🔴 P1 | バグ・リーク・データ破壊・セキュリティ・実害のある UX。ブロッキング | 3 件（超えるなら PR 分割） |
| 🟡 P2 | 保守性・可読性・将来の事故予防。非ブロッキング | 5 件 |
| 🟢 P3 | 命名・コメント・微小な API 選択。著者は無視してよい | 5 件（超過分は件数だけ） |
| 🟣 P0-pre | この PR が持ち込んだのではない既存バグ。ブロックしない。Issue にする | — |
| 💬 FYI / ✅ Good | 対応不要の参考 / 良かった点は最大 1 件、思わなければ 0 件 | — |

判断軸: 「放置したら誰がいつ困るか」を 1 行で言えるか。言えなければ P3 以下。

## 最初に問う 4 つ

- **Functionality**: 著者の意図どおりに動くか。仕様書があれば突き合わせる。エッジケース・並行性
- **Design**: この変更はこの場所に属すか。共通部品に寄せるべきではないか
- **Complexity**: 読み手が短時間で理解できるか。過剰設計・使われない汎用化。自分の指摘が過剰設計を招いていないかも見る
- **Tests**: テストが同じ PR にあり、壊したときに落ちるか。AI が書いたテストはアサーションの弱体化・skip・期待値の実装合わせを疑う

## 必ず 1 周ずつ回す観点

- **未完了リファクタ**: rename / 削除したシンボルを旧名で全体 grep し、差分外のファイルにヒットしないか
- **セキュリティ**: 外から来る値がシェル・ファイルパス・公開ディレクトリ・外部 HTTP・管理 UI に届く経路。該当なしなら「該当なし」と書く
- **認可境界**（コントローラ / routes を触る差分）: アクション × 認証 × ロール × 所有スコープ × 副作用の表を埋める。「ナビに出していない」は認可ではない
- **状態の境界**（画面）: ロード中 / 空 / エラー / 成功の 4 状態
- **根本原因**: if で症状を潰す、catch で握りつぶす、`TODO` を残す、は差し戻し

## 伝え方

- 必ず `file.ts:42` 形式の場所と「なぜ困るか」と代替コードを付ける。「ダメ」だけで終わらせない
- 禁止語: 単に / 簡単に / 明らかに / 当然 / 素晴らしい / おっしゃる通り / 必ず〜になります
- 確信度を言葉に出す。再現済みは断定、未検証は「試していませんが」、好みは「好みの範囲ですが」
- P1 以外は質問形で開く。P1 は断定する
- P1 と P3 で文章の長さを変える（P3 は 1 行）。指摘 0 件は異常ではない。件数を埋める指摘を書かない
- 証拠のない指摘をしない。挙動の主張には実コードの引用を付ける

## 報告

- md 報告は `docs/reviews/PR<番号>-レビュー結果.md`。集計行（P1: n / P2: n / P3: n）を冒頭に、動作確認セクションを末尾に
- GitHub へは行コメント・pending で投稿する（`git/pull-request.md`）
