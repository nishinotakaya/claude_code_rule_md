# Step 1-2: Plan（要件理解・計画策定）・Assess（影響範囲分析）

## Step 1. Plan — 要件理解と計画策定（重要な判断はデュアル AI）

1. 要件を理解し、方針・技術設計案を策定する。**「何を・なぜ・どこまで」を文章にする**。曖昧な点は実装前に確認する
2. **インターフェース定義**: テストエージェントが先にテストを書けるよう、以下を明確にする
   - ファイルパス（新規・変更対象）
   - クラス名・関数名・メソッドシグネチャ
   - 入出力の型・期待する振る舞い
   - API の場合: エンドポイント・リクエスト / レスポンス形式（既存の API 契約に合わせる。キーの命名・ID の型・日時の形式・エラーの形）
   - 上流工程案件（要件定義〜実装手順書がある場合）: `docs/architecture.md` のサーバー処理一覧・リポジトリ構成を出発点にし、不足分だけ補う
3. `/coding-rules` と `.claude/rules/` から、今回の変更に関連する規約・禁止パターンを抜粋する（規約全体ではなく該当部分だけ）。セキュリティに触れる変更（認証・認可・外部入力・秘密情報）は `/security-baseline` の該当項目も抜粋する
4. **重要な判断は Codex CLI にセカンドオピニオンを求める**（[dual-ai.md](dual-ai.md) 参照）。対象は設計・複数案の選択・DB 変更・API 変更・方針変更。同じ計画版で重要変更が無く、実装インターフェースまでレビュー済みなら再実施しない
5. Codex の意見を踏まえ、最終方針を確定する。反論・盲点・リスクの指摘を採否と理由付きで記録する
6. 確定した計画を `tasks/todo.md` にチェック項目付きで書く。上流工程案件では計画の正本は `docs/implementation-plan.md` とし、todo.md には手順書へのリンクと進行中の項目だけを置く
7. 3 ステップ以上のタスクは、計画をユーザーに見せて承認を取ってから着手する（プランモード。上流工程案件では実装手順書の承認が代替する）。方向違いのやり直しが一番高くつく
8. **検証手段を先に決める**: テストケース・期待出力・スクショなど「できた」の根拠を計画段階で書く。自己検証できると修正往復が減る

## Step 2. Assess — 影響範囲分析

計画策定後、コードを書く前に実施する。調査は読み取り専用の調査エージェント（researcher）に出してよい。

1. **変更対象の特定**: どのファイル・クラス・関数を変更するか列挙する
2. **依存関係の調査**: 変更対象の呼び出し元、変更対象が呼び出す先、**後続でチェーンしている処理**（API を呼んだ直後に別の API を呼ぶハンドラ、コールバック、ジョブなど）を grep で洗い出す
3. **影響範囲の判定**: 波及するモジュール・テスト・画面を特定する。rename / 削除するシンボルは旧名で全体 grep する
4. **リスク評価**: 以下を確認する
   - 既存の API レスポンス形式が変わらないか（フロントの型とバックエンドの整形メソッドの一致。フィールドは足すだけ。改名・削除は非互換）
   - 既存テストが壊れないか
   - 外部連携（決済・通知・外部 API）に影響しないか
   - DB スキーマ変更が必要か（マイグレーション・ロールバック手順・既存データの扱い・バックフィルの順序）
   - 型定義の互換性が保たれるか
   - 多テナント / 所有者スコープ: スコープが効かない経路（マイグレーション・seed・コンソール・rake・管理者 API）を通るか
   - 認可境界: コントローラ / routes を触るなら、アクション × 認証 × ロール × 所有スコープ × 副作用の表を実装前に書く
   - 旧画面・旧 API（同じモデルを使う別の入口）が壊れないか
5. **判断**: 他機能に悪影響がある場合は以下のいずれかを選択する
   - **方針変更**: 悪影響を回避できる別のアプローチを採用する
   - **実装中止**: リスクが大きすぎる場合は実装しない。ユーザーに理由を報告する

影響範囲分析の結果は `tasks/todo.md` に記録する。上流工程案件では `docs/architecture.md` の「リスクと対策」にも反映する（既存リポジトリへの追加なら「既存への影響」節を追加）。

## 計画の成果物チェック

- [ ] 「何を・なぜ・どこまで」が 1 段落で書けている
- [ ] インターフェース定義（パス・シグネチャ・型・API 形式）がある
- [ ] 関連する規約・禁止パターンを抜粋した
- [ ] 重要な判断は Codex の第二意見を取り、採否を記録した
- [ ] 検証手段（テスト・期待出力・スクショ）を決めた
- [ ] 影響範囲とリスク評価を `tasks/todo.md` に書いた
- [ ] ユーザーの承認を得た（3 ステップ以上）
