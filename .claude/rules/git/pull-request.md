# PR とレビューコメントの運用

## PR を出すとき

- `.github/pull_request_template.md` を埋める。動作確認は **実行したコマンドと結果** を貼る。未実施は「未実施」と書く
- 1 PR 1 目的。差分が大きい（目安: 10 ファイル超・500 行超）なら分割する
- フロントとバックエンドの対になる PR は、お互いの番号を本文に書く
- セルフチェック（命名・コメント・認可テスト・秘密情報・コミット対象）を通してからレビューを依頼する

## レビューコメントを投稿するとき

- 観点と優先度は `.claude/rules/review/code-review.md`、投稿の手順は `/code-review` の `references/github-posting.md`
- **指摘した行への行コメント**として付ける（Files changed タブの「+」と同じ）。Conversation に 1 本でまとめない
- **1 指摘 = 1 コメント**。作業者が 1 件ずつ resolve できる形にする
- `event` を付けずに POST して **pending（下書き）** にする。ユーザーが「投稿して」と明示したときだけ submit する
- 投稿後、実際に残っているかを API で確認してから完了報告する

## 1 指摘の文言

```
⚠️ **<一行で何がどこで問題か>（<行番号>行）**
<なぜそうなるか／何が起きるかを 1〜2 文>
```lang
// Before（<行番号>行）
<現状のコード>
// After
<修正後のコード>
```
```

- 見出しは `⚠️ **要約（行番号）**`。「注意」という語は入れない
- 締めに「〜すると安全です」を使わない。「〜で揃います」「〜が自然です」のように事実ベースで
- Before / After を必ず載せる。行番号は `grep -n` で実ファイルを確認した値
- 地の文は 1〜2 文（50〜150 字）。背景説明・再現描写・言い換えを書かない
- 行コメントに P1 / P2 / P3 のラベルを貼らない。優先度は md 報告と総評で伝える
