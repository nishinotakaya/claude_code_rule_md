# レビューコメントの書き方 — 人間の言葉で書く

> レビューは検査結果ではなく、人に読ませる手紙。読んだ人が「直したくなる」ものだけが機能する。
> 開発者が反発するのは主張の中身ではなく **書き方** に起因する（Google eng-practices）。

## 0. 大原則

**最優先: 端的に。** GitHub に貼る文章は、修正点とその直し方だけ。見出し語（総評 / P0-pre / FYI / 良い点）、背景の説明、再現の描写、丁寧語の重ねは全部削る。長い説明は md に置く。

**隣の席の先輩が、画面を指しながら口頭で説明しているように書く。** 箇条書きの羅列は検査結果。地の文で「何が起きて → なぜ困って → どう直すか」を繋ぐ。

## 1. AI っぽさの正体（これが出たら書き直す）

| 症状 | 例 | なぜダメか |
|---|---|---|
| 全部同じ熱量 | P1 も P3 も同じ長さ・同じ丁寧さ | 重要度が伝わらない |
| 迎合の定型句 | 「素晴らしい実装ですね！」「おっしゃる通りです！」 | 中身がない。1 つ出た時点で残り全部の信頼が落ちる |
| 断定の連発 | 「〜すべきです」「〜してください」が全行 | 命令の壁になる |
| 網羅の強迫 | 全ファイルに最低 1 件は付ける | 指摘ゼロのレビューは正常 |
| 用語の投げっぱなし | 「put は全置換です」 | 相手が知っている前提を勝手に置いている |
| 温度のない褒め | 「良い点: 型定義が適切です」 | 儀式に見える |
| 同じ語尾の反復 | 「〜しています。〜しています。」 | 機械が書いた合図 |
| 長すぎる | 1 指摘が 800 文字超 | 採用された指摘は平均 616 文字、無視された指摘は 807 文字 |

## 2. 禁止語彙

- 相手を小さく見せる語: 「単に」「簡単に」「〜するだけ」「明らかに」「当然」「普通は」
- 誇張: 「常に」「絶対に」「必ず〜になります」
- 「私のコード」「あなたのコード」 → コードはチームのもの。`user.rb:42` と場所で呼ぶ
- 迎合: 「素晴らしい」「完璧です」「おっしゃる通りです」「良い指摘ですね」
- ついで依頼: 「ついでにこっちも直しておいてください」 → 別 Issue に切り出して番号で参照する

## 3. 確信度を言葉に出す ★人間っぽさの最大の要素

| 確信度 | 書き方 |
|---|---|
| 確実（再現済み） | 「ここ、〜で落ちます」「〜行目で必ず nil になります」 |
| ほぼ確実だが未検証 | 「手元では試していませんが、〜になりそうです」 |
| 疑問 | 「これ、〜のケースだとどうなりますか？」 |
| 好み | 「好みの範囲ですが、〜のほうが読みやすいと思いました」 |
| 自信なし | 「見落としていたらすみません、これは意図的ですか？」 |

## 4. 命令ではなく質問で開く（ただし P1 は除く）

❌ 「この変数名を `user_id` に変更してください」
⭕ 「この変数、`user_id` のほうが意図が伝わりませんか？ 他の箇所と揃うので」

**P1（バグ・セキュリティ・データ破壊）は質問にしない。** 「〜になりませんか？」と聞くと「直さなくてもいい」と読める。事実として断言する。

## 5. 濃淡をつける

| 重さ | 地の文の目安 | 中身 |
|---|---:|---|
| バグ・データ破壊 | 〜400 字 | 何が起きるか → 再現条件 → 代替コード |
| 設計・可読性 | 150〜300 字 | 何が読みにくいか 1 文 → 理由 1 文 → 代替コード |
| 命名・コメント | 50〜150 字 | 1〜2 文で終わり。代替名だけ書く |

Before / After のコードブロックは字数に数えない。1 レビューの中で一番短い指摘と一番長い指摘が 3 倍以上開いているのが健全。返信・質問への回答も同じ上限（結論 1 文 → 理由 1〜2 文）。

### 削るときに最初に消すもの（事実・行番号・コードは最後まで残す）

1. 背景の再説明 — PR 説明文やコメントにある話は繰り返さない
2. 証跡の描写 — スクショのファイル名だけ書く
3. 「既存バグか新規か」の長い分析 — 「base 由来です」の 1 文で足りる
4. 同じことの言い換え — 「つまり」「これでは」で始まる文は前の文の重複
5. 丁寧語の重ね

## 6. インラインコメントに P1 / P2 / P3 は貼らない

優先度ラベルは md 報告とレビュー本体の総評で使う。行に貼られたラベルは成績表に見える。インラインの見出しは「通し番号 + 何が問題か」だけ。総評から番号で参照し、重さは言葉にする。バグ・セキュリティは総評の冒頭で「①はバグです」と明示し、本文も断定形。

## 7. 褒めるなら具体的に、1 件でいい

❌ 「良い点: コードが読みやすい」
⭕ 「`ArticleRepository` に永続化を寄せたの、良いと思いました。前はコンポーネントから直接 IndexedDB を叩いていたので、これでテストが書きやすくなっているはず」

基準: 自分が「へえ」と思ったかどうか。思わなかったなら書かない。

## 8. 用語は一度だけかみ砕く

❌ 「`put` は全置換です」
⭕ 「IndexedDB の `put` は『一部だけ更新』ではなく『そのレコードをまるごと置き換える』動きをします。なので createdAt を渡し忘れると既存の値が消えます」

相手が知っていそうなことは説明しない。判断がつかないときだけ 1 文添える。

## 9. 完璧を求めない

「完璧なコードなど存在しない。あるのは *より良い* コードだけ」。この変更でコードベースが良くなったなら通す。

## 10. 書いたあとの 3 チェック

1. 声に出して読めるか
2. 自分が受け取ったら直す気になるか
3. P1 だけ抜き出して読んで話が通じるか

## 11. 行番号の精度（トーンより優先）

- 見出し・本文・コードブロックのコメントの 3 箇所すべてに行番号
- 行番号は `grep -n` で実ファイルを確認した正確な値。推測で書かない
- Before / After を必ず併記し、変わった行に印を付ける

## 実例

### ❌ AI っぽい版

```
### 1. openDb() の問題 — articleDb.ts:14

**問題点**: 毎回 indexedDB.open() を呼び出しており、接続がクローズされていません。
これは明らかにリソースリークであり、単にシングルトン化するだけで解決できます。
必ずモジュールスコープでキャッシュすべきです。

**良い点**: 全体的に丁寧な実装で、型定義も適切です。素晴らしいと思います。
```

### ⭕ 人間っぽい版

```
### 1. openDb() が毎回 open していて接続が積み上がる — `articleDb.ts:14-26`

全 CRUD が毎回 `indexedDB.open()` を呼んでいて（14行目）、`db.close()` がどこにもないです。
1〜2回なら問題ないんですが、一覧画面みたいに連続で叩く画面だと接続が積み上がって、
長時間開きっぱなしにするとブラウザの接続上限に当たることがあります。

モジュール内で Promise を1本持つ形にすると、呼び出し側を変えずに済みます。

    let dbPromise: Promise<IDBDatabase> | null = null;
    function openDb() {
      if (!dbPromise) dbPromise = /* 既存の open ロジックそのまま */;
      return dbPromise;
    }
```
