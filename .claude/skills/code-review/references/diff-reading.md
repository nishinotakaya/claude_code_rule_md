# 差分を読む順序 / 打ち切り・分割要求の基準

## 読む順序（Google「Navigating a CL」）

### Step 1: そもそもこの変更は妥当か
変更の意図と説明を先に見て「この変更は作られるべきだったか」を問う。作られるべきでなかったなら、残りを読まずに却下し、代わりに何をすべきかを提案する（却下 + 代替案 + 礼儀の 3 点セット）。

### Step 2: 主要ファイルを最初に読む
論理変更が最も多いファイルを特定して先に読む。これが他の小さな変更に文脈を与える。
- ここで設計上の問題を見つけたら、残りを読まずに即座に報告する（設計をやり直すなら後続も全部やり直しになる）
- 主要ファイルが判別できないほど大きいなら、分割を要求する

### Step 3: 残りを適切な順序で
基本はツールが提示する順で全ファイル通す。テストを先に読むと変更の意図が掴めることがある。

### 全行を見る規律
- 割り当てられた全行を読む。読めないなら著者に明確化を要求する
- セキュリティの受け皿は `/security-baseline`。ただし認可境界の到達可能性表は自分で埋める
- 部分レビューで終える場合は「どの範囲を見たか」を報告に明記する

## 打ち切り・分割要求の基準

| 条件 | 対応 | 根拠 |
|---|---|---|
| 400 行 / 60 分を超えた | そこで一旦区切って報告する。続きは別ラウンド | 60 分で検出率が急落する |
| 200 行未満 | 最も欠陥を見つけられる帯。丁寧に見る | — |
| 1000 行超 or 実質 5 ファイル超 | 分割を要求する（レビュアーの正当な権利） | — |
| 全ファイル削除 | 1 行相当として扱い、規模から除外 | — |
| 自動整形・自動リファクタの生成分 | 検証のみ。規模から除外 | — |
