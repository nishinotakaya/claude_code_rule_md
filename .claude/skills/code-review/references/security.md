# セキュリティ観点（差分を読む 1 周を必ずこれに充てる）

> 構文検出（SQL・秘密リテラル）は機械側。ここは機械が構文で拾えない「データの出所と行き先」を見る。検査手順の正本は `/security-baseline`。

## 読み方

差分に出てくる **外から来る値**（params / ヘッダ / アップロードファイル名 / 外部 API の応答 / DB に保存済みのユーザー入力 / Markdown 本文）を 1 つずつ追い、どのシンクに届くかを見る。「params は直接触っていない」は安全の根拠にならない（DB 経由で別経路の入力が届く）。

## チェック表（該当するシンクがある差分は、表を埋めて報告に貼る）

| 外から来る値 | 届くシンク | 境界で何をしているか | 判定 |
|---|---|---|---|

### 1. シェル実行 → 文字列連結が 1 つでもあれば P1
バッククォート・`system("...")`・`Open3`・`IO.popen` に文字列補間があれば P1。引数は配列で渡す。HTTP を呼ぶために curl を叩いているなら Net::HTTP / Faraday に置き換える。

### 2. ファイルパス → ユーザー由来の要素が `File.join` / `Rails.root.join` に入るなら P1
`original_filename`・DB の path 列を `File.read` / `send_file` / `File.delete` に渡す前に、許可ディレクトリ配下に収まることを確認しているか。`File.extname(original_filename)` を無検証で保存名に使っていないか。

### 3. 公開ディレクトリ → `public/` 配下へのユーザーファイル保存は P1
nginx / Vite が直接配信するパスにアップロードを置くと認証を通らずに取れる。保存先は `public` 外、配信はコントローラ経由（認可付き）。

### 4. 外部 HTTP 呼び出し → タイムアウト・TLS・エラー処理の 3 点
`open_timeout` / `read_timeout` が無い Net::HTTP は相手が黙るとスレッドを永久に塞ぐ。`verify_mode = VERIFY_NONE` が差分に入ったら P1。非 2xx を握りつぶして成功扱いしていないか。URL にユーザー入力が入るなら SSRF（内部 IP・`localhost`）。

### 5. 管理 UI・デバッグ経路 → マウントに認証が無ければ P1
`Sidekiq::Web`・`letter_opener_web`・`/dev/*` を `mount` する差分は、認証ブロックがコードから読める形で付いているか。`bind '0.0.0.0'` が差分に入ったら P1。`if Rails.env.development?` で開く経路は staging が development 扱いになっていないか。

### 6. 秘密の扱い → 値ではなく「流れ」を見る
`logger.info(params.inspect)`、`raise "failed: #{response.body}"`（トークン入り）、例外通知に渡す `data:`。`.env` を新規に読む差分は git 管理外であることを報告に書く。

### 7. フロント固有
- `dangerouslySetInnerHTML` / `innerHTML` の新設。Markdown 描画は `rehype-sanitize` を外していないか
- トークンを URL クエリ・新しい localStorage キーに置いていないか
- 依存の追加は `npm audit --omit=dev` の high が増えていないか

### 8. 多テナント固有
- `unscoped` / `Model.find` の素呼び（default_scope を外していないか、外す理由がコメントにあるか）
- `tenant_id` をパラメータや URL から受けて信用していないか（`Current.tenant` が正）
- 別レコードを紐付けるとき相手が同じテナントか検証しているか
- マイグレーション・rake・seed で `Current.tenant` が nil のまま全テナントに書いていないか

### 9. 兄弟アクションの同値性
片方にガードを足したら、同じリソースを触る兄弟（`update` に足したなら `destroy` / `show` / 一覧）を全部列挙し、欠落を件数とパスで報告する。直すのは依頼された 1 つでよい。

## 報告への書き方

- セキュリティ指摘は P1 でも「誰が・どこから・何をできるか」を 1 行で書く（例: 「受講生のトークンを持つ誰でも、`user_id` を差し替えて他人の学習記録を完了にできる」）
- 到達経路が差分の外にあるときは、その経路を実コードの引用で示す。推測で P1 を付けない
- 既存コードの穴は P0-pre。ただし本 PR が新しい入力経路を足して既存の穴に届くようにしたなら P1
- 報告の「セキュリティ」欄には、シンクが無い差分でも「シェル・ファイルパス・公開ディレクトリ・外部 HTTP・管理 UI: 該当なし」と書く（見ていないのか無いのかを区別する）
- 検査コマンドの結果は「動作確認」欄に事実で書く。「brakeman が緑なので安全」とは書かない
