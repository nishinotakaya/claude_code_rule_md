# コードレビュー規約

> 目的: レビューの「視点」と「伝え方」を共通化して品質を均一にする。
> 使い方: 「レビューして」と言われたら、まずこれを読んでから差分を見る。要約は `.claude/rules/review/code-review.md`。

## 参照ファイル（必要なものだけ読む）

| ファイル | いつ読むか |
|---|---|
| `references/machine-checked.md` | **差分を読む前に必ず**。機械が潰す観点と、このプロジェクトでは人が見る観点 |
| `references/diff-reading.md` | 差分が大きい / 複数ファイルのとき。読む順序と分割要求の基準 |
| `references/llm-authored-code.md` | AI が書いたコードをレビューするとき（ほぼ常時） |
| `references/security.md` | **差分を読むとき必ず 1 周**。外から来る値がどのシンクに届くか |
| `references/tone.md` | **指摘を書くとき必ず**。AI っぽさを消す・禁止語彙・確信度 |
| `references/report-format.md` | md 報告を書くとき・指摘 0 件のとき |
| `references/github-posting.md` | GitHub PR にレビューを投稿するとき（pending の手順） |
| `references/react-typescript.md` | 差分に .ts / .tsx が含まれるとき（フロントのブランチにある） |
| `references/rails-ruby.md` | 差分に Ruby / routes / migration が含まれるとき（バックエンドのブランチにある） |

## 0. レビュー開始前の段取り

1. 対象ブランチを最新化 — `git fetch && git switch <branch> && git pull`
2. コミットを上から眺める — `git log --oneline base..HEAD`
3. `git show --stat HEAD` で変更ファイル一覧と規模を把握
4. 型・ビルド・テストを自分で通す — `npm run build` / `bundle exec rspec` / `bundle exec rubocop`
5. 未コミットの diff が混ざっていないか確認する
6. `references/machine-checked.md` を読む

報告には必ず「動作確認」セクションを設ける（型 OK / テスト OK など事実ベース）。

## 1. 指摘のラベル

| ラベル | 意味 | 上限 |
|---|---|---|
| 🔴 P1（要修正・ブロッキング） | バグ・リーク・データ破壊・セキュリティ・実害のある UX | 3 件（超えるなら分割対象） |
| 🟡 P2（改善推奨） | 保守性・可読性・将来の事故予防 | 5 件 |
| 🟢 P3（細部） | 命名・コメント・微小な API 選択。著者は無視してよい | 5 件（超過分は件数だけ） |
| 🟣 P0-pre | この PR が持ち込んだのではない既存バグ。ブロックしない。Issue 化 | — |
| 💬 FYI | 対応不要の参考 | — |
| ✅ Good | 良かった点。最大 1 件、思わなければ 0 件 | — |

判断軸: 「放置したら誰がいつ困るか」を 1 行で言えるか。言えなければ P3 以下。
既存バグを P1 に混ぜると著者の作業範囲が膨らみレビューの信頼が落ちる。「ついでに直して」と言わない。

## 2. 共通の観点

### 2.0 上位の問い（最初に問う）

- **Functionality**: 著者の意図どおりに動くか。仕様書・受け入れ基準があれば突き合わせる。エッジケース・並行性
- **Design**: この変更はこの場所に属すか。共通部品に寄せるべきか
- **Complexity**: 読み手が短時間で理解できるか。過剰設計・使われない汎用化。自分の指摘が過剰設計を招いていないか
- **Tests**: 同じ PR にテストがあり、壊したとき落ちるか。AI が書いたテストは `references/llm-authored-code.md` §2

### 2.1 責務分離 / DRY
- 永続化 / UI / ページロジックが分かれているか。同じ UI が複数ページに重複していないか
- 新規クラス・メソッドを含む差分は、既存の同等ロジック・デッドコード・名前と実体のズレを 1 周見る

### 2.2 根本原因 vs 一時しのぎ ★AI の最重要領域
- if で症状だけ潰す / catch で握りつぶす / `TODO` を残す → 差し戻し

### 2.3 エラーハンドリング・状態の境界
- ユーザー操作のエラーが画面に出るか。非同期の reject が握りつぶされていないか
- ロード中 / 空 / エラー / 成功の 4 状態が UI にあるか

### 2.4 一貫性
1. 規約（`.claude/rules/`）が絶対
2. 規約が推奨レベルなら周辺コードとの一貫性を優先
3. どのルールも無いなら既存コードとの一貫性を維持

### 2.5 ドキュメント
- 起動・ビルド・テスト手順が変わったら README / `.claude/rules/project/` も更新されているか

### 2.6 セキュリティ ★差分を読む 1 周を必ずこれに充てる → `references/security.md`
- 外から来る値がシェル・ファイルパス・公開ディレクトリ・外部 HTTP・管理 UI・ログのどこに届くか
- 認可境界（アクション × 認証 × ロール × 所有スコープ × 副作用）はコントローラ / routes を触る差分で必ず表にする
- 多テナント: `unscoped` / `Model.find` の素呼び / `tenant_id` をパラメータから受ける / `Current.tenant` が nil の経路

## 3. レビューコメントの書き方

> 必ず `references/tone.md` を読む。

- 必ず `file.ts:42` 形式の場所と「なぜ困るか」と代替コードを付ける
- 短く書く。P1 と P3 で長さを変える
- 事実（行番号・コード）は `grep -n` で確認した値。推測で書かない
- 文章の添削が要るなら Codex に出し、事実が変わっていないか再確認する（`/dual-ai`）

## 4. 報告と投稿

- md 報告 → `references/report-format.md`（`docs/reviews/PR<番号>-レビュー結果.md`）
- GitHub → `references/github-posting.md`（行コメント・pending・1 指摘 1 コメント）

## 5. 禁止事項

- 証拠のない指摘（挙動の主張には実コードの引用を必須とする）
- 「全体的に良いと思います」だけで終わる
- 優先度のない指摘リスト、コード断片のない指摘
- レビュー対象外のファイル（未コミット / 別ブランチ）を混ぜる
- 既存バグ（P0-pre）を P1 に混ぜてブロックする
- 件数を埋めるための指摘。**指摘 0 件は異常ではない**

## 6. セルフチェック（出力前）

- [ ] 全指摘にラベルと `file:line` が付いている。挙動の主張には実コード引用がある
- [ ] P1 には代替コードが付いている。P1≤3 / P2≤5 / P3≤5
- [ ] 総評に集計行がある。P1 が 0 件なら明記した
- [ ] Functionality / Design / Complexity / Tests / Consistency / Documentation / Every Line を通した
- [ ] 認可境界の表（コントローラ・routes を触る差分）・セキュリティの 5 シンク（「該当なし」を含む）を報告に書いた
- [ ] LLM 生成コードの 9 項目（`references/llm-authored-code.md`）を通した
- [ ] 禁止語彙を使っていない。確信度が言葉に出ている。P1 以外は質問形で開いている
- [ ] GitHub に出すなら pending で、インラインに P1/P2/P3 ラベルを貼っていない
