# e-learning 段階実装 PM

テックプットに e-learning を 6 フェーズで入れる。このスキルは「いまどのフェーズか」「そのフェーズで何をどこまでやるか」「いつ次へ進んでよいか」を決める。コードの書き方やテストの回し方は `/develop` に任せる。

メインセッション（CTO）が手順 1〜4 と 6〜7 を行い、手順 5 を PM に委任する。PM は渡された 1 フェーズ・1 リポジトリ分だけを進める。

## 進め方の原則

- **Phase 1〜4 は、1 フェーズ = 画面で確かめられる縦切り 1 本**。バックエンドだけ・フロントだけで終わるフェーズは作らない（Phase 0 は文書だけ、Phase 5 は検証と整理だけ）
- **バックエンド PR → フロント PR の順**。バックエンド PR は、旧フロントのままでも動く変更に限る（フィールドは足すだけで、改名・削除しない）
- **前のフェーズの完了ゲートを通るまで、次のフェーズのコードを書かない**。後のフェーズのテーブルやカラムを先取りしない

## 置き場所

| 何 | どこ |
|---|---|
| フロント | `tech-put-app/`（origin `1107t/tech-put-app`） |
| バックエンド | `teac-output-new/`（origin `nishinotakay/teac-output-new`） |
| 上流 4 文書 | `tech-put-app/docs/e-learning/` |
| 進捗の正本 | `tech-put-app/docs/e-learning/PROGRESS.md` |
| 仕様書シート（社長が見る写し） | 社長から共有された Google スプレッドシート。URL と閲覧アカウントはリポジトリに書かず、`PROGRESS.md` の先頭に置く |
| フェーズ別スコープ | `references/phases.md` |
| 現状の実コード | `references/current-state.md` |

## フェーズ一覧

| Phase | 名前 | 終わったら画面でできること |
|---|---|---|
| 0 | 要件確定 | （コードなし）未確定事項 Q1〜Q13 に答えが付き、4 文書が確定 |
| 1 | 掲載の有無と受講 | 管理者が記事を e-learning に載せる／載せないを選べる。受講生が実データのレッスンを順に読んで完了を付けられる |
| 2 | コース | 管理者がコースを作りレッスンを並べられる。受講生がコースを選んで進められる |
| 3 | カテゴリー | 管理者がレッスンにカテゴリーを付けられる。受講生がカテゴリーで絞り込める |
| 4 | 学習進捗 | 受講生が進捗率を見られる。管理者が受講状況を見られる |
| 5 | 仕上げ | seed・通しの E2E・動作確認書が揃う |

## フェーズを 1 つ進める手順

1. **現在地を読む**。`PROGRESS.md` を開き、状態が「完了」でない最初のフェーズを対象にする。ファイルが無ければ、6 フェーズ全部を「未着手」で作ってから Phase 0 を対象にする
2. **Phase 0 のとき**は要件定義 → 仕様書 → 設計書 → 実装手順書の 4 文書を確定する。`references/phases.md` の Q1〜Q13 をヒアリング項目にし、社長の返事を待つ。確定したら `phases.md` の案と食い違った箇所（API 名・テーブル名・範囲）を設計書に合わせて直し、Q13 で決まったベースブランチを `PROGRESS.md` の先頭に書く
3. **Phase 1 以降は `references/phases.md` の該当フェーズだけを読む**。次に `references/current-state.md` のうち、そのフェーズで触るファイルを実コードと突き合わせる
4. **事前承認を CTO が社長にまとめて聞く**。どのフェーズでも聞くもの: push と PR 作成、マイグレーション実行。フェーズ固有: Phase 1 は `learnings` のデータ補正を行うこと、Phase 2 は既存 e-learning 記事を既定コースへ移すこと。データ補正は二段階で、ここで取るのは「やってよいか」まで。何を何件直すかは調査後に PM が止まって CTO へ報告し、社長がその内容を見てから実行する
5. **バックエンド → フロントの順に、リポジトリごとに PM を 1 体ずつ立てて `/develop` を 1 周させる**（並走させない）。委任状の型は `.claude/rules/step/workflow-overview.md`。「許可された変更範囲」には `phases.md` のそのフェーズ・そのリポジトリの箇条書きを写し、「範囲外」の行も禁止事項として写す
6. **完了ゲート**（下記）を CTO が自分で確かめる。通らなかったら CTO が直さず、通らなかった項目を添えて PM に差し戻し、状態を実装中へ戻す
7. **進捗を書く**。`PROGRESS.md` の該当行を更新し、シートの「フェーズ一覧」の状態列を同じ値にする

`PROGRESS.md` は 1 フェーズ 1 行の表にする。`docs/` 配下なのでコミットしない。

```
ベースブランチ: フロント origin/main / バックエンド origin/feature/React

| Phase | 状態 | バックエンド PR | フロント PR | 完了日 |
| 0 | 完了 | — | — | 2026-10-03 |
| 1 | バックエンド実装中 | #301 | — | — |
| 2 | 未着手 | — | — | — |
```

| 状態 | 書き換えるとき |
|---|---|
| `未着手` | ファイルを作ったとき |
| `要件確定中` | Phase 0 で上流文書に着手したとき |
| `バックエンド実装中` | バックエンドの PM を任命したとき |
| `フロント実装中` | バックエンド PR がベースに入り、フロントの PM を任命したとき |
| `ゲート確認中` | フロント PR がベースに入ったと報告を受けたとき |
| `完了` | 完了ゲートを全部通したとき（Phase 0 は 4 文書が確定したとき） |

## 完了ゲート

全部満たしたら「完了」にする。1 つでも確かめられなければ完了にしない。

1. バックエンド: そのフェーズの request spec と RSpec 全体が通る（PM の報告ではなく自分で再実行した結果）
2. フロント: `npm run build` が通る
3. `phases.md` の受け入れ基準を Playwright で画面から確認した（PC 幅とスマホ幅）。起動方法とテストアカウントは `/auto-test`
4. 旧 ERB の `/users/learnings` と `/admins/learnings` が 500 にならない
5. 両方の PR が、`PROGRESS.md` の先頭に書いたベースブランチに入っている
6. 追加したマイグレーションが `db:rollback` で戻せる

## 全フェーズ共通の契約

`.claude/rules/project/techput-overview.md` の API 契約・テナント契約に加えて:

- **順次解放**: `locked` はサーバが計算して返し、詳細 API と完了 API でも同じ判定で拒否する。完了済みのレッスンは `locked` にしない
- **一覧**: `lessons` と `courses/:id` はページ分割しない（順次解放の判定にコース内の全件が要る）。並びは順番カラム・id の順で固定する
- **画面**: 新しいページは `UserLayout` / `AdminLayout` に載せる。`DashboardPage.tsx` のハードコードは横に新画面を足さず置き換える
- **API の形**: `references/current-state.md` の「API の書き方」に合わせる

## よくある失敗

| やりがち | 正しくは |
|---|---|
| Phase 1 のうちに `courses` テーブルも作っておく | 作らない。Phase 1 は既存の `article_type` と `learnings` だけで通す |
| フロントの PR を先に出す | バックエンド PR がベースに入ってから出す |
| 「記事を読む」ボタンを無効にして順次解放を済ませる | サーバが 403 を返すところまで作る |
| 受け入れ基準をフロントの単体テストで確かめようとする | フロントにテストランナーは無い。`npm run build` と Playwright で確かめる |
| API の向き先を `.env.local` から読む | 読まない。ポートは `teac-output-new/docker-compose.yml` を見る |
| `phases.md` に無い改善（ページネーション、通知など）を混ぜる | 範囲変更として止め、社長に聞く |
