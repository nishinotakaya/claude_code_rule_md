# STEP 6〜7: レビュー・修正

コードレビューとデザインレビューを並列で起動する。デザインレビューは UI 変更がある場合のみ。

## 6a. コードレビュー（reviewer）

```
コーディング規約とセキュリティに基づくレビューを実施してください。

## 手順
1. /code-review を読み、references/machine-checked.md で「機械が潰す観点」を頭から外す
   （このプロジェクトは lint も CI も無いので、`any`・空 catch・1 文字変数・N+1 も人が見る）
2. 変更差分を確認する: git -C <worktree> diff <base>...HEAD
3. 差分の各変更について .claude/rules/coding/ の禁止パターンに違反していないか 1 項目ずつ確認する
4. コントローラ / routes を触る差分は /security-baseline の到達可能性表を埋める
5. AI が書いたコードなので references/llm-authored-code.md の 9 項目を通す

## 出力形式
- 違反なし → 「LGTM」とだけ返す
- 違反あり → 全件列挙: [観点] ファイル:行番号 — 違反内容 — 修正方法（コード断片付き）

## 追加チェック: 設計懸念（NOTE。修正必須ではない）
- 既存の共通モジュールを使わずに同等のロジックを新規実装している
- 1 ファイルの責務が肥大化している（目安: 200 行超）
- 新しいライブラリ / パターンが既存の設計方針と一貫していない
```

## 6b. デザインレビュー（designer）— UI 変更がある場合のみ

```
実装結果のデザインレビューを実施してください。

## 手順
1. 実装された画面を Playwright で開きスクリーンショットを撮る（PC 1440 幅・スマホ 375 幅）
2. STEP 3 の UI 仕様と比較する
3. /layout-defense §2「禁止する応急処置」と §3 チェックリストで判定する

## 出力形式
- 問題なし → 「LGTM」
- 問題あり → [D-連番] 対象要素 — 問題内容 — 修正方法
```

## STEP 7. 修正

1. 指摘を分析し修正方針を決める（NOTE の採否を含む）
2. implementer で修正（テストコードは原則変更しない）
3. STEP 5.5 の品質ゲートに戻る
