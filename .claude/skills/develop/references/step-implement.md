# STEP 5: 実装（worktree 隔離）

implementer を **`isolation: "worktree"`** 付きで起動する。統合ブランチを直接汚さない。

**ゴール: STEP 4.5 で書かれたテストが全件 PASS する実装を書くこと。**

## プロンプトに含める情報

```
- 計画の要約（何を、なぜ変更するか）
- 変更対象ファイルの一覧（許可された範囲）と、触ってはいけないファイル
- 変更仕様（具体的な修正内容）
- UI 仕様（STEP 3 の出力。UI 変更がある場合）
- テストコード（STEP 4.5 の出力。このテストを通す実装を書くこと。テストは変更しない）
- 制約（壊してはいけないもの + STEP 1 で抜粋した規約）
- テックプット固有の契約（.claude/rules/project/techput-overview.md の API 契約・テナント契約）
- worktree 上でコミットすること（ステージはファイルパス明示）
```

## implementer の規律

- 1 ファイルずつ。既存コードを読んでから書く。周辺の書き方（命名・コメント密度・イディオム）に合わせる
- 要求されていないリファクタ・変更をしない
- 変更後は自分で `ruby -c` / `tsc --noEmit`（`npm run build`）を通す
- 判断に迷う仕様の穴があれば、実装を止めて質問として返す（勝手に決めない）

## STEP 5.5: 品質ゲート

| リポジトリ | コマンド |
|---|---|
| バックエンド | `bundle exec rubocop` → `bundle exec rspec` → `bundle exec brakeman -q --no-pager` |
| フロント | `npm run build` → Playwright（受け入れ基準） |

失敗した場合:
1. エラー内容を全件分析する
2. implementer で一括修正（テストコードは変更しない）
3. 再実行
4. 3 回失敗したら停止して CTO に報告する
